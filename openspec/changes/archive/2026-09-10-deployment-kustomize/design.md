# Design Document: Deployment — Kustomize & Release Images (Slice 10)

## Overview

Kustomize manifests under a new top-level `deploy/` directory, a
`goreleaser`-driven release pipeline, and a small `internal/jobs`/
`internal/orchestrator` change making the Runner image configurable
instead of hardcoded. No existing package's public behavior changes
except `internal/jobs.OperationParams`, which gains a field the same way
grpc-runner's `BaseRef` amendment already did.

## Decision 1: Kustomize layout — one base, environment overlays, an optional component

```
deploy/
  base/
    kustomization.yaml
    deployment.yaml       # Server Deployment (Requirement 1.1)
    service.yaml           # Server Service (gRPC + HTTP ports)
    serviceaccount.yaml
    role.yaml               # Jobs/Pods verbs internal/jobs.Client actually uses
    rolebinding.yaml
    configmap.yaml           # non-secret defaults (log level, ports, namespace)
  overlays/
    kind/
      kustomization.yaml    # patches image, replicas, redis address; references a pre-existing Secret
  components/
    grafana-dashboard/
      kustomization.yaml     # Kustomize Component (Requirement 1.6) — opt-in
dashboards/
  turnip.json                 # metrics slice's dashboard JSON (Slice 9, unowned by this slice)
  kustomization.yaml          # generates the labeled ConfigMap — see note below
```

`base/role.yaml` grants exactly the verbs `internal/jobs.Client` uses:
`create`/`delete`/`get`/`list`/`watch` on `batch/v1` `jobs`, `get`/`list`
on `core/v1` `pods` (Requirement 1.1's least-privilege criterion,
cross-checked directly against `internal/jobs/client.go` and
`internal/jobs/status.go`'s actual API calls rather than a broader
default).

GitHub App credentials (Requirement 1.2) are referenced by name in
`base/deployment.yaml`'s `envFrom`/`env` (`secretRef`/`secretKeyRef`), not
generated by Kustomize — an overlay either points at an
operator-pre-created Secret or layers its own `secretGenerator` on top of
the base; the base itself never embeds credential material, checked-in or
otherwise.

`base/deployment.yaml`'s `readinessProbe`/`livenessProbe` (Requirement
1.4) point at `/readyz`/`/healthz` on the HTTP port with a
`periodSeconds` short enough (`5s`) that a rolling update's default
`maxUnavailable`/`maxSurge` don't route real webhook traffic to an
instance still connecting to Redis.

The Grafana dashboard ConfigMap (Requirement 1.6) embeds the `metrics`
slice's `dashboards/turnip.json` verbatim via Kustomize's
`configMapGenerator` `files:` field — this slice packages that JSON for
deployment; it doesn't define the dashboard's content (`metrics`, Slice 9,
owns that). The generator itself lives in a new `dashboards/kustomization.yaml`
rather than under `deploy/components/grafana-dashboard/`: Kustomize
sandboxes a `configMapGenerator`'s `files:` source to the kustomization's
own directory (not configurable from `kubectl apply -k`), so a generator
under `deploy/` cannot reference a file under `dashboards/` directly.
`deploy/components/grafana-dashboard/kustomization.yaml` instead pulls in
the already-generated, already-labeled ConfigMap as an ordinary
`resources:` entry (`../../../dashboards`), which carries no such
restriction — a discovery made during implementation, documented here
since it changes where a file physically lives without changing the
outcome design.md originally described.

*Alternative considered*: a single `deploy/kustomization.yaml` with no
`base`/`overlays` split. *Rejected* — the whole point of Requirement
1.2's per-environment parameterization is that at least one more overlay
(a real production one) will exist beyond the `kind` example this slice
ships; splitting base/overlays from the start avoids a restructure the
first time a second environment shows up.

## Decision 2: `goreleaser` — adopted, single multi-image config

Requirement 2.2 asks for a documented adopt/reject decision.
**Decision: adopt.** `goreleaser` already has first-class support for
building and pushing multiple Docker images from one release (its
`dockers:` config accepts a list), which is exactly Requirement 2.3's
"both images from one release trigger" constraint — hand-rolling
equivalent `docker build`/`docker push` steps in a GitHub Actions
workflow would duplicate what `goreleaser` already does correctly
(multi-arch tags, `:latest` + versioned tag both pushed, changelog
generation from conventional commits), for no benefit over adopting it.

*Alternative considered*: two independent `docker/build-push-action`
steps in `.github/workflows/`, one per image. *Rejected* — nothing
enforces the two images come from the same git tag/commit unless they're
both driven by the same release event; two independent Actions steps
*can* be made to do that with care, but `goreleaser`'s single
`.goreleaser.yaml` makes it the default rather than something every
future workflow edit has to remember to preserve.

`.goreleaser.yaml` sketch: two `dockers:` entries (`turnip-server`,
`turnip-runner`), each building from `build/server/Dockerfile` /
`build/runner/Dockerfile` (already exist, Slice 0) with
`image_templates: ["ghcr.io/ivanvc/turnip-server:{{ .Tag }}", ".../turnip-server:latest"]`,
triggered by a new `.github/workflows/release.yml` on `v*` tag push.

## Decision 3: `runnerImage` becomes a Server config value, not a package constant

`internal/jobs/build.go`'s `runnerImage` is currently:

```go
// TODO: This should point to the released version.
runnerImage = "ghcr.io/ivanvc/turnip-runner:latest"
```

**Resolution**: `BuildJob` gains a `RunnerImage string` field on
`OperationParams` (mirroring how `CommitSHA`/`BaseRef` already flow
through that struct — grpc-runner's `BaseRef` amendment is the direct
precedent), sourced from a new `TURNIP_RUNNER_IMAGE` environment variable
read into `orchestrator.Config` and passed through `New(...)`'s existing
wiring to wherever `OperationParams` is built in `execute.go`.
`TURNIP_RUNNER_IMAGE` is a required env var (`ConfigFromEnv` rejects it
unset, same as every other required value) and `runnerImage` is no longer
a package constant in `internal/jobs` at all — turnip has no released
version and no external caller yet, so there's nothing for a fallback to
be compatible *with*; keeping one would just be complexity against a
hypothetical caller. `deploy/base/kustomization.yaml`'s `configMapGenerator`
ships a real default value for it (matching the base Server image's own
default tag), which an overlay overrides alongside the `images:`
transformer (Decision 1) — same overlay-level source of truth, enforced
by the config now refusing to start without it rather than by a
code-level fallback.

## Decision 4 (amendment): a downloadable, per-release install manifest

Added after this slice was first marked complete, per user feedback:
`docs/deployment.md` (the `ha-validation` slice's Requirement 2) was
telling operators to hand-copy `deploy/overlays/kind/` — a local-testing
overlay pinning a `dev` image tag — as if it were a production starting
point. Every other Kubernetes project's install story is "download one
YAML from the release, `kubectl apply -f` it"; turnip's Kustomize
base/overlay split (Decision 1) is the right shape for *authoring*
per-environment manifests, but isn't by itself an install artifact an
operator can point `kubectl apply -f` at without cloning the repo first.

**Resolution**: a new `deploy/overlays/release/kustomization.yaml` —
`deploy/base` plus the `images:`/`TURNIP_RUNNER_IMAGE` overrides Decision
1 already established, both left as literal `:latest` placeholders. A new
`.github/workflows/release.yml` step ("Render install manifest"), running
*before* the `goreleaser-action` step, `sed`-substitutes those
placeholders for `${GITHUB_REF_NAME}` (the pushed tag) and renders the
whole overlay via `kubectl kustomize` into `dist-manifests/turnip-install.yaml`
— deliberately a directory other than goreleaser's own `dist/`, since
goreleaser cleans that directory at the start of every run (confirmed
empirically: a file placed in `dist/` ahead of time doesn't survive to the
upload step). `.goreleaser.yaml` gained a `release.extra_files:` entry
pointing at that path, so goreleaser uploads it as a GitHub Release asset
alongside the checksums file — no new dependency, this is goreleaser's
own documented mechanism for attaching arbitrary files to a release.

The substitution step needed two separate `sed` rules, not one: `images:`
transformer's `newTag: latest` (space after the colon, a YAML
`key: value` pair) and the `TURNIP_RUNNER_IMAGE` ConfigMap literal's
`turnip-runner:latest` (no space, an image-reference string) don't share
a common substring — a single `s/:latest/:$TAG/` pattern silently missed
the first one entirely, caught only by rendering and inspecting the
output before wiring it into CI, not by `goreleaser check`'s config-schema
validation (which has no way to know what the rendered YAML *contains*).

`docs/deployment.md`'s primary install path is now
`kubectl apply -f https://github.com/ivanvc/turnip/releases/download/vX.Y.Z/turnip-install.yaml`
(or `/releases/latest/download/...` — GitHub's own stable "latest
release" URL convention) followed by `kubectl set env` for the two
values Requirement 1.3 deliberately leaves unset
(`TURNIP_REDIS_ADDR`/`TURNIP_GITHUB_APP_ID`) and creating the credentials
Secret. `deploy/overlays/kind/` is now documented purely as a local-dev
example; hand-maintaining a live overlay is demoted to an explicitly
opt-in "Alternative" for GitOps users, with `deploy/overlays/release/` as
its suggested starting point.

*Alternative considered*: keep `turnip-install.yaml` builds a no-op
(since goreleaser also pushes `:latest`-tagged images, an operator could
in principle build their own manifest referencing `:latest` and never
touch a version at all). *Rejected* — that's exactly the moving-target
problem this slice's own Requirement 2 ("a real, reproducible version tag
... not a moving `:latest` tag") already ruled out for the images
themselves; the install manifest shouldn't reintroduce it one level up.

## Package Layout

```
internal/jobs/build.go            // amended: OperationParams.RunnerImage (Decision 3)

deploy/                            // NEW — Kustomize (Decision 1)

```

## Dependencies

No new Go dependency. `goreleaser` is a build-time tool (installed in CI,
not imported by any Go package).

## Testing Strategy

- **Unit tests**: `internal/jobs/build_test.go` gains a case asserting
  `BuildJob` uses `OperationParams.RunnerImage` verbatim for the Runner
  container's image; `internal/orchestrator/config_test.go` gains a
  round-trip case and a missing-var case for the new required env var.
- **Manifest validation**: `deploy/base` and `deploy/overlays/kind` are
  validated with `kubectl kustomize deploy/overlays/kind | kubeconform
  -strict -summary` in CI (a new step, not a Go test) — catches malformed
  YAML and invalid API fields against the real Kubernetes OpenAPI schemas,
  without needing a real cluster. `kubectl apply --dry-run=client -f -`,
  this section's original plan, turns out to require a live, reachable API
  server even in dry-run mode (its REST discovery step calls the server
  unconditionally) — confirmed during implementation, not just a
  theoretical concern — so it can't satisfy "without needing a real
  cluster" at all; `kubeconform` (offline JSON-schema validation against
  Kubernetes' published schemas) is the tool that actually does.
- Actually applying the overlay to a real `kind` cluster and asserting
  the Server comes up healthy is `ha-validation`'s concern (Slice 11,
  Requirement 1.5) — this slice proves the manifests are well-formed and
  internally consistent, not that they produce a working deployment
  end-to-end.
- No property tests — this slice is manifests and build-pipeline
  configuration, not application logic.

## Backward Compatibility

N/A — turnip has no released version and no external callers of
`internal/jobs`/`internal/orchestrator` yet, so `OperationParams.RunnerImage`
and `Config.RunnerImage` are plain required fields with no fallback
behavior to design for. `execute.go`, this package's only real caller, is
updated in the same change. No other exported signature changes.
